# 物序 ERP

面向制造与医院耗材业务的中文 ERP 原型。浏览器、Python API 与 PostgreSQL 使用同一套库存事件模型。Docker Compose 启动两个服务，数据库保存在命名卷，只有网页端口对宿主机开放。首版面向单组织、多仓业务。

## 从 GitHub 拉取镜像

仓库的 `main` 分支推送后，GitHub Actions 会构建镜像，用 PostgreSQL 启动 Compose 并检查登录和急单自动演示。检查通过后先发布 `sha-<提交号>` 镜像，再通过 Compose 回拉启动。回拉健康检查通过后才更新 `main` 标签。默认部署镜像为 `ghcr.io/kinsanka/wuxu-erp:main`，首次发布成功后即可拉取。当前工作流构建 Linux x86-64 镜像。

在能访问仓库和容器注册表的主机上执行以下命令。若镜像是私有的，先执行 `podman login ghcr.io -u kinsanka`，在终端输入对该软件包有读取权限的 GitHub Personal Access Token（classic，`read:packages`）。

```bash
git clone https://github.com/kinsanka/wuxu-erp.git erp_workbench
cd erp_workbench
if [ ! -e .env ]; then
  (
    umask 077
    python3 - <<'PY'
import secrets

with open(".env", "x", encoding="utf-8") as config:
    for name in ("ERP_ADMIN_PASSWORD", "ERP_DB_PASSWORD"):
        print(f"{name}={secrets.token_urlsafe(24)}", file=config)
PY
  )
fi
podman compose pull
podman compose up -d --no-build
podman compose ps
```

在 Docker 主机上，将 `podman compose` 换为 `docker compose`，私有镜像可通过 `docker login ghcr.io -u kinsanka` 登录。部署其他仓库的镜像或固定某次提交时，在 `.env` 中设置 `ERP_IMAGE`。更新时，在原部署目录以同一 Compose 项目名执行 `git pull --ff-only`、`podman compose pull` 和 `podman compose up -d --no-build`，沿用同一个 PostgreSQL 卷。

打开 [http://localhost:8787](http://localhost:8787)，以 `admin` 和 `.env` 中的 `ERP_ADMIN_PASSWORD` 登录。默认端口仅绑定本机。登录后从侧栏进入「急单协同演练」并点击「自动演示」。

## 用本地源码构建

解压后进入与 `compose.yaml` 同级的目录，需要 Docker 和 Docker Compose v2。先按上面的方式生成 `.env`，也可参考 `.env.example` 分别设置管理员及数据库口令。首次构建会下载 Python、PostgreSQL 镜像和 Python 依赖。

```bash
ERP_IMAGE=wuxu-erp:local docker compose up -d --build
docker compose ps
```

打开 [http://localhost:8787](http://localhost:8787)，用 `admin` 和部署时设置的管理员密码登录。如在 NAS 上运行并打算从另一台设备访问，在现有 `.env` 中将 `ERP_BIND` 设置为 NAS 局域网 IP。

首次初始化时会生成工厂仓、医院中心库和手术室二级库，以及示例供应商、物料、库存、采购、制造工单、销售与耗用单。重启会保留操作数据。查看状态与日志：

```bash
docker compose ps
docker compose logs --tail 60 app db
```

健康检查为 `GET /api/health`，Compose 版返回 `{"ok": true, "db": "postgresql"}`。

## 急单协同演练

登录后在侧栏进入“急单协同演练”。该页将研究报告第五章和配套 Excel 的 `SO-SIM-001` 转成可逐步操作的案例。每个账号有独立演练进度，可在页面确认后重置。演练事件、模拟库存、应收和应付保存在演练数据中。

点击 **自动演示**，播放器会从基准案例开始依次展示 29 个节点。时间进度条、完成步骤数、当前处理事项、下一节点剩余时间、交付情况、物料可用量和应收余额随模拟变化。可暂停、继续、按“下一步”定位到下一个完成节点、从头播放或选择 0.5×、1×、2×、4×。离开页面或切至其他浏览器标签时会暂停。

默认 1× 时，播放 1 秒相当于 3 小时模拟时间。从 11 月 16 日 08:30 到 26 日 16:00，完整播放约 83 秒。例中给审批、收货、质检排队、生产、运输、周末和对账分配了模拟时间，可同时展示独立进行的任务。具体小时数和最后一笔 400 元回款为演示设定。两次预期拦截会在记录里显示实际校验结果。自动演示使用独立的基准场景，手动演练进度和业务账不参与播放。


1. **11 月 16 日，核对急单。** 客户要求 30 套于 11 月 20 日到达。核对 REV-B、信用和日产能，先登记一次交付首版，再登记客户确认的 20+10 套分批版。确认两条记录和客户原要求都保留。为第 1 批锁料，分别记录 PO-A、PO-B 的 ASN。
2. **11 月 17 至 19 日，收货、检验并发首批。** 17 日实收 PO-B，完成第 1 批并出库发运。18 日登记第 1 批到货签收和验收，放行 PO-B，实收 PO-A。19 日放行 PO-A，再尝试给第 2 批锁料。可在放行前尝试锁料，对比实收待检和质检放行前后的可用量。
3. **11 月 20 至 23 日，发剩余 10 套并核收。** 20 日完工发运、23 日签收和验收。两批全部验收后，登记模拟销售发票、授权贷项和实收核销。独立的采购核账例先核实 PO 20、合格 GR 18、供方发票 20 的 2 件差异，登记发票修正为 18 后再确认应付。
4. **重复演练异常。** 修改信用、版本或 PO 确认条件，重算并验证承诺被拦截。把某物料实物改成小于冻结加预留的数量，观察短差和阻断。查看异常责任岗位、跟进期限、签收及验收凭证、承诺版本，以及安全库存四种情景。

基准复核结果为现货齐套 20 套，壳体净缺 5、执行器净缺 20、包材净缺 0，全量最早 11 月 23 日到达。配套 Excel 将首批 11 月 18 日列作到达日，报告正文同日写作发运。演练采用 Excel 的时点口径，按一工作日运输，分别列出首批 11 月 17 日发运和 18 日到达，第二批 11 月 20 日发运和 23 日到达。供应商预计实收到货日补设为 18 日（PO-A）及 17 日（PO-B），预计质量可用日期按原表。当前承诺可以在实际锁料前修订，执行后变更和多订单并行分配未纳入本演练。

## 功能与数据规则

- **采购、销售**。往来单位、多行单据、审核、部分收货或发货。采购登记批号和效期，销售按仓库和 FEFO 顺序从已放行、未过期的批次发货。单价字段用于业务查看。前端对相同表单的短期重试复用请求标识，已成功入账的重试会返回原结果。
- **制造**。BOM 版本、工序和工单关联。审核通过后，按整单计算材料需求并按 FEFO 扣料。工序依序记录工时，整单完工登记新的产出批次，成品经人工检验放行后进入可用库存。缺料表按单层 BOM、当前仓库存和计划日期内可见采购计算，未为其他单据执行库存预留。
- **质量与仓储**。每个批次拥有全仓一致的待检、放行或冻结状态。需要检验的收货批次进入待检，包括已放行批次再次到货的情况。两条调拨流水和包装码位置在同一事务更新。到期日当天仍可用，从次日开始停止发货、生产领用、调拨和耗用。业务日期默认使用北京时间。
- **医疗耗材**。医院中心库、手术室二级库、按包装码逐件调拨、手术业务号关联耗用、费用回执待对账／退回／确认。支持普通包装码和 GS1 AI `01`、`17`、`10`、`21` 的子集。GS1 至少要有已绑定的 GTIN 和序列号。可输入括号文本或带 `]d2` 前缀及 ASCII 29 分隔符的扫描结果。变长字段在后续还有字段时须保留分隔符。GS1 AI `17` 采用实际日历日。
- **控制**。账户角色分为管理员、采购／计划、仓储／质检、临床耗材、只读。业务写入在 API 检查角色；临床对账记录仅管理员和临床角色可查，完整审计仅管理员可查。库存和常规单据是组织内共用数据。每次数量变动生成流水；改变库存、包装码和单据进度须在同一数据库事务成功。数量最多 3 位小数，入库和出库都按物料主计量单位登记。
- **报表**。运营总览、效期和补货点预警、分仓库存、临床对账、审计与 CSV。界面加载最近 300 张单据、200 条流水、200 个包装码、300 条耗用记录和 200 条审计记录。包装码可用精确追溯查询较早记录，CSV 导出整个相应报表。

## 模式、备份与扩展

从空库试运行时使用独立的 Compose 项目，设置以下变量。新建管理员初始密码和 PostgreSQL 密码各用独立随机值且至少 14 位。密码使用 `.env` 的单引号格式，避免含美元符号时被 Compose 插值。

```dotenv
ERP_DEMO=0
ERP_ADMIN_PASSWORD='替换为独立长密码'
ERP_DB_PASSWORD='替换为另一独立长密码'
```

```bash
docker compose -p wuxu-erp pull
docker compose -p wuxu-erp up -d --no-build
```

同时运行两个实例时，请给不同实例设置不同的宿主端口。数据库名称和卷与项目绑定。已有数据库卷应沿用已配置的数据库口令，修改环境变量不会重置卷中的 PostgreSQL 角色密码。首次启动成功后，管理员密码由应用内「更改密码」维护。HTTPS 反向代理部署时保留 Host 请求头并设置 `ERP_SECURE_COOKIE=1`。

```bash
docker compose exec -T db pg_dump -U erp -d erp -Fc > erp-backup.dump
```

备份可用于单独的空库恢复验证，恢复前应确认目标服务器与库名。审计是应用内的操作记录，数据库管理员可以访问底层数据。

首版适合流程原型与评估。完整总账、税票、多组织、寄售结算、HIS/SPD 实际接口、病历、退货冲正、多阶时段 MRP、详细成本核算和监管验证留待后续实现。医疗示例使用虚构业务号，试用无需录入患者身份信息。

本地界面调试可用 Python 3.11+ 和 SQLite，无需安装包，Windows 可用 PowerShell 设置相应环境变量。它与 Compose 的 PostgreSQL 使用不同数据文件。

```bash
set -a
. ./.env
set +a
ERP_SQLITE=erp-preview.sqlite3 python3 app/main.py
```

本机入口为 [http://localhost:8080](http://localhost:8080)。回归测试使用临时 SQLite，不污染现有数据：

```bash
python3 -m unittest discover -s tests -v
```

## 验证状态

本地回归覆盖 HTTP 路由、登录退出、CSV、部分收货的短期重试、FEFO、冻结、并发重复耗用、跨模块批次追溯、库存回滚和首次初始化。急单回归覆盖分批到货验收、超占阻断、权限隔离、应收应付分账及自动演示的只读隔离。容器端的 PostgreSQL、登录和自动演示由发布工作流验证。
